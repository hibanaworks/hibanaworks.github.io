Hibana — Choreographic Programming in Rust

GitHub API docs 日本語

Describe who sends what to whom, and in what order.

Hibana is a Rust library for choreographic programming. You write one shared protocol and each participant's Rust code. Hibana derives the communication steps for each participant and checks its sends and receives at runtime.

Participants can be tasks in one program or programs on different machines. The core uses no_std, requires no heap allocator, and runs on stable Rust 1.95 or newer. Your program supplies its memory.

Add to your project

cargo add hibana@0.9.7

Or add it to Cargo.toml:

[dependencies]
hibana = "0.9.7"

Hibana 0.9.7 on crates.io · MIT or Apache-2.0

A small exchange

A client sends a number. The server adds one and sends it back. Write that order once:

use hibana::g;

const CLIENT: u8 = 0;
const SERVER: u8 = 1;
type Request = g::Msg<1, u32>;
type Reply = g::Msg<2, u32>;

let exchange = g::seq(
    g::send::<CLIENT, SERVER, Request>(),
    g::send::<SERVER, CLIENT, Reply>(),
);

Each participant gets an endpoint, a handle for its part of the protocol:

Client

client.send::<Request>(&7).await?;
let answer = client.recv::<Reply>().await?;

Server

let number = server.recv::<Request>().await?;
server.send::<Reply>(&(number + 1)).await?;

These are excerpts. The complete example also supplies memory and a transport, then attaches both endpoints. Receiving the reply before sending the request compiles as Rust, but Hibana returns an error because the operation is out of order.

Protocols can also describe choices, independent communication in parallel, and repetition.

QUIC and TLS

hibana-quic

QUIC v1/v2 and HTTP/3. It uses Hibana for communication among packet processing, TLS, transmission, and timers. Applications can also write a shared protocol for messages sent over QUIC.

The hello-quic example sends numbers from a client and returns their squares from a server. Both use endpoints derived from the same application protocol.

hibana-tls

TLS 1.3 handshake and authentication for hibana-quic. Its protocol describes the order of transcript checks and key handoff. Cryptographic operations and certificate checks are implemented in Rust.

It provides TLS for QUIC, with no TCP TLS records or TLS socket API.

Both libraries use Hibana 0.9.7. They are experimental. Hibana's protocol proofs do not prove the correctness of their QUIC or TLS implementations.

How it works

One global protocol, one local protocol per role

In multiparty session types (MPST), a global protocol describes communication among all participants. Endpoint projection derives a local protocol for each role. Hibana performs this projection through Rust's const evaluation and rejects protocols that fail its checks during compilation.

You write the participant functions and their computations in Rust. Projection produces protocol data for each role. An endpoint tracks its progress through that data rather than changing its Rust type after every operation.

Choices must reach the roles that need them

A role must learn which branch was chosen before it acts differently in that branch. This is knowledge of choice. Hibana checks incoming messages for that evidence during projection. It rejects choices it cannot check under its current rules. It does not add broadcasts, so include any messages needed to inform another role.

Errors and progress

The runtime checks the next operation, peer, message kind, and payload format before advancing. Previewing a branch does not advance it. A successful send means that the transport accepted the message, not that the peer received it.

The transport supplies deadlines and reports I/O errors. A transport error ends the current session run. To communicate after a timeout, include that outcome in the protocol or begin a fresh run after failure.

Hibana checks communication against the local protocol. It does not inspect running tasks to detect or repair deadlock cycles. The Lean proofs establish properties for their stated models. Applying protocol deadlock freedom to a running system also requires an accepted protocol, matching peers and codecs, a conforming transport, and fair scheduling.

For the API, transport contract, and exact proof assumptions, see the README. The direct research inspiration is affine multiparty session types (AMPST).
